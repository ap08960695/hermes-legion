# Role Based Routing

Use before assigning a specialist. Match the required capability to an authorized available lane, including suitable Web bots. Check native eligibility, quota, cooldown, tools and modality. Do not infer availability from a label or SDK type. Preserve saved session model bindings unless a model change is authorized. On refusal, respect the native cooldown and no-paid-fallback policy.

Distinguish the role, native profile, provider pool and underlying account. Provider twins share a family contract; public-only Web specialists cannot receive confidential work. Count duplicate aliases of an account against one actual quota scope. Prefer the existing session's route/account where eligible; unavailable pinned work stays held rather than silently switching. A dry-run recommendation neither pins a native credential nor reserves live quota. Recheck the current native account selection, claims, profile/host/project capacity and gates before real dispatch. Do not copy OAuth token files or edit a running bot to implement a recommendation.

Use only existing authorized provider lanes and native quotas. No paid fallback, allowance probes or model-backed polling. Preserve owner decisions, rights, review and publication gates. Do not interrupt active workers or modify unrelated services. Report meaningful completion, failure or a material owner question; stay quiet on unchanged waits. Role guidance confers no additional tool or filesystem permission.
